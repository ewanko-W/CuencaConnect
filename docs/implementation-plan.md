# CuencaConnect: Implementation Plan for the Prototype (Revision 2)

## Context
The repository holds only `CLAUDE.md` (one commit, `b869b89`). CuencaConnect is a capstone prototype for the Municipality of Cuenca, Batangas, with three areas:
- a **mobile-first, installable PWA** at `/app` for residents;
- a **centralized command dashboard** at `/admin` for municipal administrators;
- an **office inbox** at `/office` for staff of responding offices (MDRRMO, BFP, PNP, MHO, Engineering, etc.).

**Changes in Revision 2**
- **Resident ID verification:** residents must be verified before they can report or vote.
- **Manual routing:** reports are routed by an admin. Automatic routing is removed, and triage only *suggests* an office.
- **New role and status:** an `office_staff` role, and a `routed` report status.

**Decisions confirmed by the user**
| Topic | Decision |
|---|---|
| Supabase | Develop on the local Supabase CLI (Docker); deploy the same migrations to a free Supabase Cloud project for the demo |
| Votes | One upvote per **verified** resident per report; it raises the priority score |
| Alerts | Sent to the whole municipality or to selected barangays; readable by unverified users |
| PWA | Installable, offline app shell, offline report queue, Web Push, and in-app alerts through Realtime |
| Verification | Register with consent → upload a government ID photo → `pending` → an admin approves or rejects with a reason. The ID number is never stored. ID images are purged 7 days after the decision. |
| Routing | Centralized: the triage suggests an office, and an admin routes the report at `/admin/command` |

**Guiding principle:** business logic lives in Postgres, through constraints, triggers, `SECURITY DEFINER` RPCs and RLS. Edge Functions are used only where privileged Storage or external calls are unavoidable (signed URLs, purging, Web Push). The React client stays thin. All data is simulated (Data Privacy Act of 2012).

## 1. CLAUDE.md update (first commit of Phase 0)
Change the **Rules** section so it reads:
- Roles: `resident`, `office_staff`, `admin`, stored in `profiles.role`. Admins and office staff are created manually, never by public sign-up. Office staff must have `profiles.office_id`.
- Residents must be **ID-verified** before submitting reports or voting. Unverified users may read alerts and the office directory only.
- Registration requires explicit consent (recorded with a version and timestamp).
- Store only the ID type and verification status, **never the ID number**. ID images live in a private bucket. They are viewed only through ~60-second signed URLs from an Edge Function that writes an `audit_log` row per view, and are purged 7 days after the decision.
- Routing is centralized: triage sets only `suggested_office_id`. Only admins route reports, through `route_report`, which writes `routing_history` and `audit_log`.
- Office staff see only reports assigned to their office.
- Critical reports are always visible to **all admins**, whether routed or not and regardless of votes.
- Every new rule needs a pgTAP test.

The existing rules (RLS over guards, editable EN/FIL keywords, no secrets, mobile-first, HTTPS, Data Privacy Act) remain.

## 3. Database schema (PostGIS, pg_cron and pg_net enabled)

**Enums**
- `user_role`: resident, office_staff, admin
- `verification_status`: unverified, pending, approved, rejected
- `report_category`: fire, flood, medical, crime, road, utilities, waste, other
- `report_severity`: low, medium, high, critical
- `report_status`: submitted, **routed**, acknowledged, in_progress, resolved, rejected, duplicate
- `alert_level`: advisory, warning, emergency
- `keyword_lang`: en, fil

| Table | Key columns | Constraints and notes |
|---|---|---|
| **profiles** | `id → auth.users`, `role default 'resident'`, `office_id → offices (null)`, `display_name`, `barangay_id`, `phone (null)`, `verification_status default 'unverified'`, `consent_version`, `consented_at`, `created_at` | CHECK: `role = 'office_staff'` requires `office_id`, and other roles must have none. A trigger blocks non-admin changes to `role`, `office_id` and `verification_status`. |
| **accepted_id_types** | `id`, `name` (e.g., PhilSys National ID, Driver's License, UMID, Passport, Postal ID, Voter's ID, Barangay ID), `requires_back bool`, `is_active` | Admin-editable list |
| **id_verifications** | `id`, `user_id`, `id_type_id`, `front_path`, `back_path (null)`, `status (pending/approved/rejected)`, `rejection_reason`, `submitted_at`, `reviewed_by`, `reviewed_at`, `images_purged_at` | **No ID-number column.** Partial UNIQUE index: one `pending` per user. CHECK: `rejected` requires a reason. Resubmission after rejection is allowed. |
| **reports** | `id`, `client_uuid UNIQUE`, `reporter_id`, `category`, `title`, `description`, `location geography(Point)`, `barangay_id`, `severity`, `is_critical`, `matched_keywords text[]`, **`suggested_office_id`**, `assigned_office_id (null until routed)`, `status`, `vote_count`, `priority_score`, timestamps, `resolved_at` | The location must fall inside the municipal bounding box. GiST index on the location; index on (`status`, `is_critical`, `priority_score`). |
| **routing_history** | `id`, `report_id`, `from_office_id`, `to_office_id`, `routed_by`, `note`, `created_at` | Append-only |
| **report_media** | `id`, `report_id`, `storage_path`, `mime_type`, `size_bytes`, `uploaded_by` | At most 3 images, 5 MB each |
| **report_votes** | PK (`report_id`, `voter_id`), `created_at` | No self-vote; voter must be verified |
| **alerts** | `id`, `created_by`, `title`, `body`, `level`, `scope`, `target_barangay_ids`, `starts_at`, `expires_at`, `is_active` | `scope = 'barangay'` requires targets |
| **offices** | `id`, `name`, `hotline`, `contact_info`, `handles_categories[]`, `is_active` | Also serves as the public directory |
| **keywords** | `id`, `term`, `lang`, `category`, `severity_weight`, `is_critical`, `is_active`, `updated_by`, `updated_at` | UNIQUE (lower(term), lang) |
| **audit_log** | `id`, `actor_id`, `action`, `table_name`, `record_id`, `old_data`, `new_data`, `created_at` | Append-only; no UPDATE or DELETE for anyone |
| *Supporting:* **barangays** | `id`, `name`, `boundary geography(MultiPolygon)` | Simplified or simulated boundaries |
| *Supporting:* **push_subscriptions** | `id`, `user_id`, `endpoint UNIQUE`, `p256dh`, `auth` | Web Push |
| *Supporting:* **alert_reads** | PK (`alert_id`, `user_id`), `read_at` | Read/unread state |

### Database functions and triggers

**Identity and roles**
1. `handle_new_user()`: creates a `profiles` row with `role = 'resident'` and `verification_status = 'unverified'`. It refuses to create the profile if the consent fields in the sign-up metadata are missing.
2. Helper functions (`STABLE SECURITY DEFINER`): `is_admin()`, `is_office_staff()`, `my_office_id()`, `is_verified()`.

**Verification**
3. `submit_verification(id_type_id, front_path, back_path)`: an RPC for residents in the `unverified` or `rejected` state. It checks that the paths sit under `/{uid}/` in the `id-documents` bucket and that a back image is present when the ID type requires one. It inserts a `pending` row, sets `profiles.verification_status = 'pending'` and writes `audit_log`.
4. `review_verification(verification_id, decision, reason)`: an admin-only RPC. It rejects self-review, requires a reason when rejecting, sets the row and the profile status plus `reviewed_by`/`reviewed_at`, and writes `audit_log`.

**Reports**
5. `triage_report()`: a BEFORE INSERT/UPDATE trigger. It matches EN and FIL keywords, then sets `severity`, `is_critical`, `matched_keywords`, `barangay_id` (via `ST_Contains`) and **`suggested_office_id` only**. It never sets `assigned_office_id`.
6. `route_report(report_id, office_id, note)`: an admin-only RPC. It allows `submitted → routed` and re-routing of `routed`/`acknowledged` reports. It sets `assigned_office_id`, inserts `routing_history` and writes `audit_log` explicitly.
7. `set_report_status(report_id, new_status, note)`: an RPC that checks permissions by role.
   - **Office staff** (own office only): `routed → acknowledged → in_progress → resolved`, or `return_to_command`, which goes back to `submitted` with a required reason and clears the assignment.
   - **Admins:** may additionally set `rejected` or `duplicate`, and may reopen reports.
   - Every change is logged.
8. `recompute_priority()`: a vote trigger that maintains `vote_count` and `priority_score`.
9. `nearby_reports(lat, lng, radius_m)`: an RPC returning anonymized summaries.

**Audit, alerts and scheduled jobs**
10. `audit_trigger()`: attached to `profiles`, `id_verifications`, `reports`, `routing_history`, `alerts`, `offices`, `keywords` and `accepted_id_types`.
11. Alert insert trigger: calls the `send-push` function via `pg_net`.
12. pg_cron jobs: a **daily** call (via `pg_net`) to the `purge-id-images` Edge Function.

### Edge Functions
| Function | Behaviour |
|---|---|
| `id-image-url` | Validates the caller's JWT and calls `is_admin()`. It refuses if the images are already purged, creates a **60-second** signed URL with the service role, and inserts `audit_log` (`action = 'id_image_view'`, the verification id and which side). It returns only the URL. |
| `purge-id-images` | Protected by a cron secret. It selects decided verifications where `reviewed_at < now() - 7 days` and `images_purged_at IS NULL`. It deletes the objects through the Storage API, nulls the paths, sets `images_purged_at` and writes `audit_log`. |
| `send-push` | Resolves the alert's target users and sends Web Push messages with VAPID keys. |

## 5. Row Level Security outline
RLS is enabled on every table. Each policy uses the helper functions listed in §3.

| Table | Resident (unverified) | Resident (verified) | Office staff | Admin |
|---|---|---|---|---|
| profiles | Own row: SELECT/UPDATE of safe columns | same | Own row | SELECT all |
| accepted_id_types | SELECT active | SELECT active | none | CRUD |
| id_verifications | SELECT own (status and reason); INSERT only via RPC | SELECT own | **none** | SELECT; decisions only via RPC |
| Storage `id-documents` (private) | INSERT to `/{uid}/`; **no SELECT** | same | none | **no direct SELECT**; signed URL only via the Edge Function |
| reports | **no INSERT** | INSERT own; SELECT own; UPDATE own while `submitted` | SELECT/UPDATE (through the RPC) where `assigned_office_id = my_office_id()` | SELECT **all** with no predicate besides `is_admin()`, so critical reports are always visible |
| report_media and its bucket | none | own reports | reports assigned to the office | all |
| routing_history | none | none (the timeline shows the office name via the reports view) | SELECT for the office's reports | SELECT all; INSERT only via `route_report` |
| report_votes | **no INSERT** | INSERT/DELETE own | none | SELECT |
| alerts | SELECT active and targeted | same | SELECT active | CRUD |
| offices (directory), barangays | SELECT active | same | SELECT | CRUD |
| keywords | none | none | none | CRUD |
| audit_log | none | none | none | SELECT only; no UPDATE or DELETE for anyone |
| push_subscriptions | CRUD own | CRUD own | CRUD own | own; the Edge Function uses the service role |

Office staff see the reporter's display name only; contact details stay hidden for data minimization.

## 6. PWA installability
- **Tooling:** `vite-plugin-pwa` in `injectManifest` mode.
- **Manifest:** `start_url: /app`, `scope: /app/`, `display: standalone`, icons (including maskable), screenshots, theme colour. The admin and office areas are not part of the installed app.
- **Service worker:** precaches the app shell; NetworkFirst for API GETs; CacheFirst for OSM tiles, with limits; `offline.html` as the fallback page.
- **ID images are never cached.** The service worker bypasses `id-documents` and signed URLs, and the verification upload is **online-only**, so ID data is never stored on the device.
- **Offline report queue:** IndexedDB with Background Sync, plus a retry when the device comes back online. Each report carries a `client_uuid` to prevent duplicates. The queue is available only to verified users; a server rejection is shown if the user's verification has changed.
- **Push:** VAPID keys (public key in `.env.example`, private key in Supabase secrets). Permission is requested from a user action. An iOS hint explains that push requires the installed app on iOS 16.4+.
- **Install:** a `beforeinstallprompt` button, plus iOS instructions. The demo is served over HTTPS.

## 8. pgTAP coverage of the new rules (minimum)
**Verification**
- An unverified or pending resident cannot INSERT into `reports` or `report_votes`; a verified resident can.
- Unverified users can SELECT targeted alerts and active offices.
- `id_verifications` has no column resembling an ID number, which is asserted through a schema test.
- Rejecting without a reason fails; self-review fails; a non-admin calling `review_verification` fails; there can be only one pending verification per user.
- Residents cannot change their own `verification_status`, `role` or `office_id`.
- No role has SELECT access on `storage.objects` in `id-documents`.
- The purge selection includes only decisions older than 7 days; purged rows have null paths.
- A missing consent value blocks profile creation.

**Routing and offices**
- The triage trigger never sets `assigned_office_id`.
- `route_report` is admin-only, writes `routing_history` and `audit_log`, and sets `routed`.
- Office staff SELECT only `assigned_office_id = my_office_id()`, cannot call `route_report`, and cannot set `rejected` or `duplicate`.
- Every admin can SELECT critical reports whether routed or unrouted.
- Status transitions outside the allowed graph are rejected.
- `audit_log` rejects UPDATE and DELETE.

Edge Functions get Deno unit tests: signed-URL expiry is 60 s, a view writes an audit row, and non-admin callers are refused.

## 9. Verification strategy
- **Database:** `supabase test db` (pgTAP).
- **Edge Functions:** `deno test`.
- **Front end:** Vitest with React Testing Library (guards, `VerificationGate`, offline queue with `fake-indexeddb`).
- **End-to-end:** Playwright smoke flow: register → verify → admin approves → report → Command routes → office resolves → resident sees "Resolved"; alert to Barangay.
- **Manual:** the Lighthouse PWA audit, and device install tests on Android Chrome and iOS Safari 16.4+.

## 10. Assumptions (non-blocking; will be documented as limitations)
- Verification relies on a visual check by an admin; there is no OCR or government database lookup.
- Pending verifications are not purged automatically; only decided ones are, 7 days after the decision.
- A verified resident remains verified unless an admin revokes the status, which is logged.
- Barangay boundaries are simplified polygons.
- English is the default UI language.
